## Главное впечатление

Для такой утилиты задача небольшая, поэтому не стоит сразу строить сложную архитектуру с большим количеством классов и «сервисов». Достаточно разделить приложение на несколько самостоятельных частей:

1. **Получение настроек**
   - аргументы командной строки;
   - JSON-файл;
   - интерактивный ввод.

2. **Проверка настроек**
   - существуют ли исходные папки;
   - доступна ли целевая папка;
   - корректны ли пути.

3. **Копирование**
   - создание папки запуска;
   - обход файлов;
   - копирование отдельных файлов;
   - обработка ошибок отдельных файлов.

4. **Логирование**
   - создание файла журнала;
   - запись `INFO`, `DEBUG`, `ERROR`.

5. **Точка входа**
   - запуск сценария;
   - обработка критической ошибки;
   - код завершения программы.

Зависимости лучше направить в одну сторону:

```text
main
 ├── получает настройки
 ├── создаёт logger
 └── запускает copier

copier
 └── не должен знать о argparse или JSON

settings/config
 └── отвечает только за получение и проверку настроек
```

То есть копировщик не должен сам читать аргументы командной строки, спрашивать пользователя или открывать JSON-файл. Это сильно упростит тестирование.

# Замечания по текущим файлам

## `main.py`

В `src/main.py`:

- импортируется `create_argparser`, но он не используется;
- импортируется `filelog`, но также не используется;
- вместо запуска приложения выполняется только `print("Hello world")`;
- пока отсутствует вся последовательность запуска.

`main.py` должен быть максимально коротким. В нём не стоит размещать логику копирования. Его задача — связать компоненты:

```text
получить настройки
создать журнал
создать копировщик
запустить копирование
обработать критическую ошибку
```

## `Settings`

В `src/app/models/Settings.py`:

```python
class Settings():
```

Для Python более привычный стиль:

- имя класса — `Settings`;
- скобки после имени класса обычно не пишутся;
- поля имеют типы;
- для простой структуры данных обычно используют `dataclass`.

Сейчас объект создаётся пустым, а потом изменяется через `get_settings`. Это менее удобно и позволяет получить частично заполненные настройки.

Концептуально лучше, чтобы настройки создавались уже готовыми:

```text
Settings(
    sources=[...],
    target=...,
    log_level=...
)
```

Даже если фактический код пока не писать, именно так лучше мыслить о модели: `Settings` — это не сервис и не загрузчик, а обычный объект, содержащий уже подготовленные настройки.

Также сейчас отсутствует уровень журналирования, хотя в README он предусмотрен.

## `SettingsFileException`

В `src/app/exceptions/SettingsFileException.py` исключение технически допустимо, но:

- имя файла по Python-конвенции должно быть в нижнем регистре, например `settings_file_exception.py`;
- отдельное исключение имеет смысл, если приложение действительно по-разному обрабатывает ошибки файла настроек;
- не нужно создавать собственные исключения для каждой мелкой ошибки.

Можно разделить ошибки на две категории:

### Ошибки настроек

Критические:

- JSON невозможно прочитать;
- обязательное поле отсутствует;
- путь имеет неправильный формат;
- не удалось получить настройки.

### Ошибки отдельных файлов

Некритические:

- один файл недоступен;
- один файл удалён во время копирования;
- нет прав на чтение;
- файл невозможно записать.

Вторая группа не должна останавливать копирование остальных файлов.

## `cli.py`

В `src/app/services/cli.py` есть важная ошибка:

```python
"--output"
"-o"
```

Между строками отсутствует запятая. В Python две строковые константы подряд объединяются, поэтому фактически получится один параметр:

```text
--output-o
```

Это нужно исправить до реализации.

Другие замечания:

### `--input` сейчас не принимает коллекцию

В README и PLAN указано несколько исходных папок, но текущий аргумент описан как одно значение.

Нужно заранее выбрать один из вариантов интерфейса:

- несколько аргументов `--input path1 --input path2`;
- несколько путей после одного аргумента;
- повторяемый короткий параметр `-i path1 -i path2`.

Для такой задачи наиболее понятен вариант с повторяемым аргументом.

### `--verbose` недостаточен

В README заявлены уровни:

- `ERROR`;
- `INFO`;
- `DEBUG`.

Флаг `--verbose` обычно означает только включение подробного режима. Нужно решить, будет ли:

- `--verbose` включать `DEBUG`;
- или использовать параметр вроде `--log-level INFO`;
- или оставить оба варианта.

Если уровень должен быть также в JSON, лучше иметь единую модель настройки `log_level`.

### `color=True`

Параметр `color=True` зависит от версии Python. Если проект не ограничен современной версией Python, это может привести к несовместимости. В плане стоит явно указать минимальную версию Python.

## `filelog.py`

В `src/app/services/filelog.py` сейчас есть несколько проблем.

### Асинхронность здесь пока не нужна

Комментарии говорят об асинхронных методах, но для обычной консольной утилиты это усложнит проект:

- файловые операции не становятся автоматически эффективнее из-за `async`;
- потребуется асинхронный `main`;
- нужно будет везде использовать `await`;
- обычные файловые функции Python синхронные.

Для этой задачи лучше использовать стандартный модуль [`logging`](https://docs.python.org/3/library/logging.html), а не создавать собственную обёртку вокруг записи строк.

Стандартное логирование уже умеет:

- уровни `DEBUG`, `INFO`, `ERROR`;
- запись в файл;
- формат даты и времени;
- создание отдельного файла;
- вывод в консоль;
- обработку исключений.

Собственный `FileLog` имеет смысл только как очень тонкий адаптер, если требуется скрыть детали настройки стандартного логгера.

### В методах отсутствует `self`

Сейчас написано:

```python
async def log_error(message):
```

Если это методы экземпляра класса, должен учитываться объект журнала. Иначе методы будут работать некорректно. Но предпочтительнее не исправлять это отдельно, а сначала решить, нужен ли вообще собственный класс.

## `copier.py`

В `src/app/services/copier.py` сейчас нет реализации.

Для копировщика важно заранее определить его ответственность:

### Копировщик должен

- принять готовые настройки;
- создать каталог конкретного запуска;
- пройти по исходным каталогам;
- скопировать доступные файлы;
- отдельно обработать ошибку каждого файла;
- вернуть итоговую статистику.

Например, итоговая информация может включать:

- сколько файлов найдено;
- сколько скопировано;
- сколько пропущено;
- сколько ошибок;
- путь к созданной папке.

### Копировщик не должен

- читать аргументы командной строки;
- самостоятельно читать JSON;
- спрашивать пользователя;
- сам настраивать глобальную систему логирования.

Это разные уровни приложения.

# Что стоит изменить в PLAN

Текущий `PLAN.md` полезен как черновик сценария, но его нужно немного переработать.

## 1. Разделить источники настроек и обработку настроек

Сейчас в одном алгоритме смешаны:

- аргументы;
- JSON;
- интерактивный режим;
- логирование;
- копирование.

Лучше записать явно:

```text
1. Прочитать аргументы командной строки.
2. Если аргументы полные — использовать их.
3. Если аргументов нет — попробовать прочитать JSON.
4. Если JSON отсутствует — запросить параметры в консоли.
5. Проверить итоговые настройки.
6. Настроить логирование.
7. Выполнить копирование.
8. Вывести итог.
```

Важно определить, что происходит при **частичных аргументах**. Например, передан источник, но не передана целевая папка. Есть два разумных варианта:

- считать это ошибкой;
- недостающие параметры запросить интерактивно.

Для консольной утилиты первый вариант проще и предсказуемее.

## 2. Исправить терминологию

В README говорится о папках, а в PLAN местами написано «каждый указанный файл из исходников».

Нужно выбрать основную модель:

- пользователь указывает исходные папки;
- программа копирует файлы внутри них.

Это важное уточнение, потому что копирование отдельных файлов и копирование дерева каталогов — разные сценарии.

## 3. Уточнить структуру результата

Нужно заранее решить, как копируются несколько исходных папок:

```text
target/
    2026-09-23_16-30-00/
        source_1/
        source_2/
```

или все файлы складываются непосредственно в одну папку.

Если складывать всё в один каталог, одинаковые имена файлов могут конфликтовать. Для резервного копирования обычно безопаснее сохранять структуру исходных каталогов.

## 4. Уточнить поведение при ошибках

Рекомендуемая политика:

| Ситуация | Поведение |
|---|---|
| Неверный JSON | завершить программу с ошибкой |
| Не указан обязательный путь | завершить программу с ошибкой |
| Исходная папка не существует | ошибка настроек или пропуск — выбрать явно |
| Нет доступа к одному файлу | записать `ERROR`, продолжить |
| Не удалось создать целевую папку | завершить программу |
| Неожиданное исключение | записать traceback, завершить программу |
| Часть файлов скопирована, часть нет | завершить с предупреждением или специальным кодом |

Особенно важно различать:

- ошибку одного файла;
- невозможность выполнить сам запуск.

Для текущего размера приложения я бы рекомендовал такую логическую структуру:

```text

            setup.py
```

Но это не означает, что все файлы нужно создавать сразу.

Минимальный практичный вариант:

```text

    app/
        settings.py
        copier.py
        logging_config.py
```

Начать лучше с минимального варианта. Отдельные классы и файлы стоит добавлять только когда появляется реальная ответственность.

# Рекомендуемый порядок реализации

## Этап 1. Минимальное копирование

Сначала реализовать только:

- источник;
- целевую папку;
- копирование;
- обработку ошибок;
- базовое логирование.

Без JSON и интерактивного режима.

## Этап 2. Аргументы командной строки

Добавить:

- один или несколько источников;
- целевой путь;
- уровень журналирования.

## Этап 3. JSON

Добавить загрузку настроек из JSON, если аргументы не переданы.

JSON должен иметь простой и предсказуемый вид:

```text
sources: список исходных каталогов
target: целевой каталог
log_level: уровень журнала
```

## Этап 4. Интерактивный режим

Только после этого добавлять вопросы пользователю в консоли. Иначе получится слишком много вариантов поведения одновременно, которые сложно проверять.

## Этап 5. Тесты

Минимальный набор тестов:

- успешное копирование;
- несколько исходных папок;
- создание отсутствующей целевой папки;
- недоступный файл;
- отсутствующий источник;
- неправильный JSON;
- конфликт имён;
- пустой источник;
- повторный запуск.

# Что считать «принятым» стилем Python

Для этого проекта достаточно следующих правил:

- файлы и функции — `snake_case`;
- классы — `PascalCase`;
- константы — `UPPER_CASE`;
- не использовать `get_settings`, который меняет состояние объекта;
- добавлять типы к публичным функциям;
- использовать `pathlib.Path` вместо ручной работы со строками путей;
- использовать стандартный `logging`;
- не добавлять `async`, если нет настоящей асинхронной задачи;
- не превращать каждую операцию в отдельный класс;
- один модуль должен иметь одну понятную ответственность;
- `main.py` должен быть тонким координатором.

## Итог

Основная проблема сейчас не в том, что выбраны «неправильные классы», а в том, что пока не определены границы ответственности:

- кто получает настройки;
- кто проверяет настройки;
- кто копирует;
- кто логирует;
- какие ошибки критические;
- как сохраняется структура нескольких источников.

Я бы рекомендовал сначала переработать PLAN вокруг этих пяти компонентов, затем реализовывать по этапам. Текущую папку `services` не нужно заполнять большим количеством классов: для небольшого приложения лучше несколько простых функций и один основной компонент копирования, чем сложная Java-подобная иерархия.
